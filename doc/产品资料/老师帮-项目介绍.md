# 老师帮项目介绍

> 项目名称：老师帮  
> 分析范围：PC 管理端 `teacher_help_admin`、后端服务 `teacher_help_service`  
> 分析日期：2026-06-11

## 1. 项目定位

老师帮是一套面向教培机构、独立教师和小微教学团队的教务管理系统。项目目标是把学员管理、学员家长/联系人信息、老师管理、课程套餐、班级排课、点名考勤、上课记录、物品费用、会员卡、场地预约和后台权限管理整合到一个统一的管理平台中，帮助教师和运营人员降低日常教务、沟通和数据维护成本。

从现有代码和文档看，项目采用 PC 管理后台 + 后端 API 服务的前后端分离架构。PC 端承担运营管理、教务操作和系统配置；后端提供登录认证、权限控制、基础系统管理、教学业务接口、物品费用接口、代码生成和监控能力。

## 3. 技术架构

### 3.1 PC 管理端

PC 端位于 `teacher_help_admin`，整体沿用 RuoYi-Vue3 的前端工程形态。

核心技术栈：

- Vue 3.4 + Vite 5
- Element Plus 2.7
- Pinia
- Vue Router 4
- Axios
- Sass
- FullCalendar，用于课表/日历类场景
- ECharts、Vue Quill、文件上传、图片裁剪等后台常见能力

关键工程特征：

- `src/main.js` 统一注册 Element Plus、全局组件、全局方法、权限指令、插件和 SVG 图标。
- `src/router/index.js` 定义公共路由、助教业务路由和动态权限路由。
- `src/permission.js` 负责登录态校验、用户信息拉取、动态路由注入和页面跳转控制。
- `src/utils/request.js` 封装 Axios，请求自动携带 `Authorization: Bearer <token>`，统一处理错误码、重复提交、防抖和下载。
- `vite.config.js` 开发端口为 `8081`，开发环境 `/dev-api` 代理到后端 `http://localhost:9099`。

PC 端页面分为两类：

- `src/views/system`、`src/views/monitor`、`src/views/tool`：RuoYi 系统管理、监控和代码生成能力。
- `src/views/teach`、`src/views/assistant`：老师帮业务页面，包括教师、学生基础档案、学员、课程、班级、课表、上课记录、物品费用等；会员卡和场地管理目前主要体现在产品原型和总结文档中。

### 3.2 后端服务

后端位于 `teacher_help_service`，整体基于 RuoYi-FastAPI 风格实现。

核心技术栈：

- FastAPI 0.115
- Uvicorn
- SQLAlchemy 2 异步 ORM
- asyncmy / PyMySQL，MySQL 驱动
- asyncpg，PostgreSQL 支持
- Redis
- APScheduler
- Pydantic / pydantic-settings
- PyJWT + passlib/bcrypt
- loguru
- openpyxl / pandas，用于 Excel 导入导出

后端启动入口为 `app.py`，应用组装集中在 `server.py`：

- 创建 FastAPI 实例。
- 生命周期中初始化数据库表、Redis 连接池、系统字典缓存、系统参数缓存和定时任务调度器。
- 加载静态子应用、中间件和全局异常处理。
- 统一注册系统管理、教学管理、物品费用管理和代码生成路由。

配置由 `config/env.py` 通过 `.env.dev`、`.env.prod` 等环境文件加载（这两个文件不入库，从 `teacher_help_service/.env.example` 复制后填写；生产环境必须设置 `JWT_SECRET_KEY`），支持应用配置、JWT 配置、数据库配置、Redis 配置、代码生成配置和上传配置。数据库连接在 `config/database.py` 中创建，默认支持 MySQL，也保留 PostgreSQL 切换能力。

## 4. 后端分层设计

后端采用典型的 Controller -> Service -> DAO -> Entity 分层。

```text
controller/  # FastAPI 路由层，负责接口声明、权限依赖、请求参数和响应封装
service/     # 业务逻辑层，负责校验、事务、数据组装和业务规则
dao/         # 数据访问层，负责 SQLAlchemy 查询和持久化操作
entity/do/   # 数据库实体模型，映射数据表
entity/vo/   # 请求/响应模型，基于 Pydantic
```

典型调用链以学生管理为例：

```text
src/api/teach/student.js
  -> /teach/student/list
  -> module_teach/controller/teach_student_controller.py
  -> module_teach/service/teach_student_service.py
  -> module_teach/dao/teach_student_dao.py
  -> module_teach/entity/do/teach_student_do.py
```

后端在接口层通过 FastAPI 依赖和装饰器挂接通用能力：

- `LoginService.get_current_user`：登录态和当前用户解析。
- `CheckUserInterfaceAuth`：接口权限校验。
- `GetDataScope`：数据权限范围控制。
- `@Log`：操作日志记录。
- `@ValidateFields`：Pydantic 字段校验增强。
- `ResponseUtil`：统一响应结构。
- `PageUtil`：统一分页结构。

## 5. 主要功能模块

### 5.1 系统基础能力

来自 `module_admin` 和 PC 端系统管理页面，主要包括：

- 登录、注册、验证码、退出登录。
- 用户、角色、菜单、部门、岗位管理。
- 字典、参数、通知公告管理。
- 操作日志、登录日志、在线用户管理。
- 定时任务、缓存监控、服务监控。
- 代码生成工具。

这部分是 RuoYi 系管理后台的基础能力，也是老师帮业务权限、菜单和审计体系的底座。

### 5.2 教学管理模块

后端位于 `module_teach`，PC 端接口位于 `src/api/teach`，已形成教师、学生基础档案、家长/联系人基础信息、排课和考勤的业务骨架。这里的 `/teach/parent` 是基础数据接口，不代表当前 PC 原型中存在独立“家长管理”业务模块；按原型口径，家长信息应归入学员档案的联系人/关联人能力。

核心接口模块：

- `/teach/teacher`：教师管理。
- `/teach/student`：学生管理。
- `/teach/parent`：家长/联系人基础信息。
- `/teach/schedule/event`：排课事件管理。
- `/teach/schedule/attendance`：排课考勤管理。

核心实体包括：

- `TeachBaseUser`：基础用户。
- `TeachTeacher`：教师信息。
- `TeachParent`：家长信息。
- `TeachStudent`：学生档案。
- `TeachScheduleEvent`：排课事件。
- `TeachScheduleAttendance`：考勤记录。
- `TeachSubject`、`TeachGrade`：科目和年级基础数据。

### 5.3 助教业务页面

PC 端 `src/views/assistant` 下沉淀了更贴近实际教培机构操作流的页面：

- 学员管理：在读学员、报读情况、报名、详情、跟进、转课、停课等场景。
- 课程管理：课程、套餐、收费方式等场景。
- 班级管理：班级列表、详情、班级点名、排课、调课等场景。
- 课表管理：时间课表、老师课表、教室课表、班级课表。
- 上课记录：点名记录、点评记录、请假申请、缺课提醒、补课等场景。
- 物品/费用：物品管理、SKU、采购、领用、退领、盘点、费用项目等场景。
- 会员卡：课程卡、场地折扣卡、卡详情、发放记录等场景，当前主要体现在 `doc/产品图片/8会员卡` 和模块总结文档中。
- 场地管理：场馆、场地、订场管理、锁场、预订记录、核销、取消预订等场景，当前主要体现在 `doc/产品图片/9场地管理` 和模块总结文档中。

这些页面功能形态较完整，和 `doc/产品图片` 中的产品截图对应度较高。当前产品图片共 9 个业务模块、168 张图片；不少页面仍使用前端模拟数据，适合作为业务原型和后续接口对接依据。

### 5.4 物品费用模块

后端位于 `module_ast`，当前已实现物品管理接口：

- `/ast/item/list`
- `/ast/item/{item_id}`
- `/ast/item`
- `/ast/item/{item_ids}`

`module_ast/README.md` 当前标注：物品管理、SKU 管理、出入库管理、采购导入、费用项目和选择项接口已经具备独立管理与演示能力。PC 端 `assistant/inventory` 已经有较完整的交互页面；后续完整业务闭环重点是继续对接课程套餐、学员报名订单、支付流水和财务账。

### 5.5 代码生成模块

`module_generator` 保留了 RuoYi 风格的代码生成能力，可以从数据库表生成 Python、Vue、SQL 等模板代码。该能力对后续快速扩展业务 CRUD 模块很有价值。

## 6. 数据与接口约定

### 6.1 统一响应

后端通过 `ResponseUtil` 统一接口响应结构，典型格式如下：

```json
{
  "code": 200,
  "msg": "操作成功",
  "success": true,
  "time": "2026-06-11T12:00:00",
  "data": {},
  "rows": []
}
```

列表分页一般返回：

```json
{
  "rows": [],
  "pageNum": 1,
  "pageSize": 10,
  "total": 0,
  "hasNext": false
}
```

### 6.2 字段命名

后端数据库实体以 snake_case 为主，Pydantic VO 模型大量使用：

```python
ConfigDict(alias_generator=to_camel, from_attributes=True)
```

这使得接口层可以把后端字段转换为前端习惯的 camelCase，例如 `student_name` -> `studentName`、`create_time` -> `createTime`。

### 6.3 权限体系

前后端采用统一权限标识：

- 后端接口依赖：`CheckUserInterfaceAuth('teach:student:list')`
- 前端按钮权限：`v-hasPermi="['teach:student:list']"`

权限命名一般遵循：

```text
模块:资源:操作
```

例如：

- `teach:student:list`
- `teach:student:add`
- `teach:student:edit`
- `teach:student:remove`
- `ast:item:list`

## 7. 代码风格总结

### 7.1 PC 端代码风格

PC 端整体是 RuoYi-Vue3 的后台管理风格，偏向“表格 + 查询表单 + 工具栏 + 弹窗/抽屉 + 分页”的业务后台写法。

主要风格特征：

- 使用 Vue 3 Composition API，页面多采用 `<script setup>`。
- Element Plus 组件使用密集，表单、表格、弹窗、抽屉、标签、分页和按钮是主要交互单元。
- 每个业务域在 `src/api` 中维护独立 API 文件，例如 `teach/student.js`、`teach/schedule.js`。
- 页面内常用 `ref`、`reactive`、`toRefs` 管理查询参数、表单、列表、加载状态和弹窗状态。
- 沿用 RuoYi 的全局工具方法，例如 `proxy.$modal`、`proxy.resetForm`、`proxy.useDict`、`parseTime`。
- 按钮级权限通过 `v-hasPermi` 控制。
- 样式以 SCSS 为主，业务页面常使用 scoped style。

需要关注的现状：

- `assistant` 业务页面功能很完整，但单文件较大，后续可按列表、表单、弹窗、详情抽屉拆分组件。
- 部分页面存在模拟数据、硬编码字典和本地状态流转，正式联调时需要替换为后端接口。
- 项目标题、包名和部分 README 仍保留“若依/RuoYi”信息，产品化时建议统一替换为“老师帮”。

### 7.2 后端代码风格

后端是清晰的异步 FastAPI 分层风格，整体强调统一封装和模板化扩展。

主要风格特征：

- 路由层使用 `APIRouter(prefix=...)` 定义模块接口。
- Controller 方法显式声明 `Request`、Pydantic 查询模型、`AsyncSession`、当前用户和数据权限依赖。
- Service 使用类方法组织业务逻辑，负责事务提交/回滚和业务异常。
- DAO 使用 SQLAlchemy `select`、`join`、`where`、`order_by` 构建异步查询。
- DO 模型映射数据库表，VO 模型承载请求、响应和字段校验。
- 统一使用 `ResponseUtil.success/failure/error` 返回结果。
- 统一使用 `PageUtil.paginate` 处理分页。
- 逻辑删除字段常见为 `del_flag`。
- 注释和 docstring 以中文为主，可读性较强。

需要关注的现状：

- 个别状态字段在前端、VO 和 DO 中存在字符串/数字混用，后续建议统一字典和值类型。
- DAO 中存在 `eval(data_scope_sql)` 方式处理数据权限表达式，后续应谨慎评估安全性和可维护性。
- 部分 JSON 字段既使用数据库 JSON 类型，又在 Service 中手动 `json.dumps/json.loads`，建议统一序列化策略。
- 部分异常捕获较宽泛，后续可补充更明确的业务异常和日志上下文。

## 10. 项目总结

老师帮当前是一套以 RuoYi 生态为基座的教培管理系统。它的优势在于后台权限、菜单、日志、监控、代码生成等基础能力成熟，后端分层清楚，PC 端业务页面覆盖面广，且产品文档和截图资料充足。

后续建设重点应放在三件事上：

1. 将 `assistant` 下的业务原型页面逐步接入真实后端接口。
2. 补齐学员报名订单、课时账户、班级、上课记录、会员卡、场地等核心业务后端模块。
3. 统一产品命名、状态字典、字段类型和代码组织，减少模板遗留痕迹。

整体而言，项目已经具备“可扩展后台管理平台”的基础骨架，适合继续沿着现有 Controller-Service-DAO 分层和 RuoYi 前端规范迭代业务功能。
