## 一、核心结论（TL;DR）

1. **设计文档的 `ast_*` 教学表是废稿**：真实库教学域全是 `teach_*`，`ast_*` 只剩物品费用 8 张。设计里的 `ast_class_record / ast_student_comment / ast_leave_application` 等**一张都不存在**——这就是上课记录的点评/请假至今只能 mock 的根因。
2. **🔴 真实高危：两套考勤表 status 枚举冲突且已串味**。班级点名会把新枚举值无映射直接写进旧考勤表，`status=4` 在两表语义相反（未到↔缺勤）。
3. **🟡 真实 bug ×2**：① 4 处旧表软删写错 `del_flag` 值；② 学生 `status` 编码实体(0-3) 与 VO(1-4) 整体错位，导致新建学生存成"休学"、在读筛选查不到人。
4. **🟢 虚惊澄清：不存在"双报名台账"问题**。旧 `teach_course_enrollments`/`teach_courses`/`teach_course_consume_logs` 代码零引用，是死表，新表（enrollment_order + student_course_account）是唯一真实台账。

## 三、🔴 高危：两套考勤表 status 枚举冲突（已串味）

### 事实

| 表 | 用途 | status 枚举（DO 注释） |
| --- | --- | --- |
| `teach_schedule_attendances`（旧） | 课表签到/考勤，`/teach/schedule/attendance` 用 | **0未到 1出勤 2迟到 3请假 4缺勤**（`teach_schedule_attendance_do.py:16`） |
| `teach_class_attendance_detail`（新） | 班级点名/上课记录，`/teach/class` `/teach/class-record` 用 | **1到课 2迟到 3请假 4未到**（`teach_class_do.py:145`） |

冲突在 **status=4 和 status=0**：旧表 `4=缺勤`、新表 `4=未到`；旧表 `0=未到`（默认值且签到逻辑强依赖），新表无 0。1/2/3 恰好同义（到课≈出勤、迟到、请假），**掩盖**了 4/0 的不对齐。

### 已确认的串味路径（核心证据）

班级点名提交 `submit_class_attendance_services` 通过 `event_id` 桥接，**反写旧表且无枚举映射**：

```
teach_class_service.py:738-745
  if page_object.event_id:
      schedule_attendance.status = item.status   # ← 把新枚举(1-4)直接塞进旧表
```

- `teach_class_service.py:740`：前端新枚举 `item.status`（4=未到）**未经映射**赋给 `teach_schedule_attendances.status`（4=缺勤）。
- 同一条物理记录：新表口径"未到"，旧表统计 `teach_schedule_attendance_dao.py:124` 计入 `absent`（缺勤）。
- 点名准备页 `get_attendance_prepare_services`（`teach_class_service.py:551`）反向拿旧表 status 套新表标签字典：旧表历史 `status=0` 会命中 `.get(0,'到课')` → **把"未到"显示成"到课"**。

### 风险判定：高

| 串味场景 | 等级 |
| --- | --- |
| status=4 跨表写入（未到↔缺勤口径相反） | 高 |
| status=0 语义在点名后被抹平 / 统计桶错位 | 中 |
| 旧表 0 值被新枚举字典误读为"到课" | 中 |

**根因**：`teach_class_service.py:740` 在两套不同 status 字典间做了无映射直接赋值。
**修复方向**：在反写旧表处加 `新→旧` 枚举映射函数（如 `4→4` 改为按语义 `未到→缺勤` 显式映射，并处理旧表 0 值），或彻底统一两表为单一枚举。

## 四、🟡 真实 bug ×2：软删与状态编码

> 背景：库是 MySQL（`config/database.py:9`），`varchar = int` 走隐式转换（`'0'=0` 为真），所以下面的 bug 在 MySQL 下"侥幸能跑"，但已写入脏值、且迁移 PostgreSQL 即崩。

### Bug A — 4 处旧表软删写错 del_flag 值（中高）

旧代次表约定"删除 = `'2'`（字符）"，但以下 4 处写成数字 `1`：

| 文件:行号 | 代码 | 应为 |
| --- | --- | --- |
| `teach_student_dao.py:154` | `student.del_flag = 1` | `'2'` |
| `teach_teacher_dao.py:144` | `teacher.del_flag = 1` | `'2'` |
| `teach_parent_dao.py:141` | `parent.del_flag = 1` | `'2'` |
| `teach_base_user_dao.py:99` | `user.del_flag = 1` | `'2'` |

影响：int `1` 入 `varchar(1)` 存成 `'1'`，查询 `del_flag==0` 下 `'1'≠0` 仍能排除，**软删侥幸生效**；但库内已删标志是 `'1'` 而非约定 `'2'`，任何依赖 `del_flag='2'` 的外部 SQL/报表/修复脚本会漏判。对照：`teach_schedule_event_dao.py:124` 正确写 `'2'`。

### Bug B — 学生 status 编码实体与 VO 整体错位（高 · 数据正确性）

| 层 | 文件:行号 | status 取值域 |
| --- | --- | --- |
| 实体 DO | `teach_student_do.py:28` | **0在读** 1休学 2转学 3毕业（默认 `'0'`） |
| VO | `teach_student_vo.py:26/52/91` | **1在读** 2休学 3转学 4毕业（`Literal['1','2','3','4']`） |

错位后果：
- 新建学生：`teach_student_service.py:238` 把 VO 的 `'1'`（本意"在读"）写入 DB，但 DB 里 `'1'=休学` → **新生默认被存成"休学"**。
- 在读筛选：`teach_student_dao.py:54` `status == query_object.status` 字符等值，前端传 `'1'` 想查在读，但库里在读是 `'0'` → **查不到真正在读的学生**。

**修复方向**：统一学生 status 编码（建议二选一并全链路对齐：要么 DO 改 1-4，要么 VO 改 0-3），并出数据修复脚本回填存量错值。

### 附带规范隐患（非 bug）

旧表过滤软删大量用数字 `0`（如 `teach_student_dao.py:38`），与正确的字符 `'0'` 写法（如 `teach_schedule_event_dao.py:33`）混用，靠 MySQL 隐式转换生效，**不可移植到 PostgreSQL**。

## 五、🟢 澄清：不存在"双报名台账"问题（旧表已死）

曾怀疑旧 `teach_course_enrollments`（钱包式）与新 `teach_enrollment_order + teach_student_course_account` 双活不一致。核实后排除：
