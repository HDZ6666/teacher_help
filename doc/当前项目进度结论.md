# 当前项目进度结论

> 更新时间：2026-06-25
> 检测范围：`teacher_help_admin`、`teacher_help_service`、`teacher_help_uniapp`、`doc`、`teacher_help_service/logs`、真实 MySQL 库结构核查结论。
> 说明：本文件记录当前实际代码进度。旧版 `PC前后端代码与产品原型一致性审查.md` 中关于班级后端缺失等结论已经过期；2026-06-25 新增的 `数据库真实结构与后端技术债核查_2026-06-25.md` 是后端真实库和数据正确性风险的最新补充。

## 总体结论

项目当前不是“全模块完成”，而是已经形成了两条较清晰的业务基础链路：

1. 课程、物品/费用、学员报名/续费已经具备较高完成度，并开始形成跨模块联动。
2. 班级基础管理、报名入班、班级学员、未排课直接点名、消课和点名详情已经打通基础闭环。

业务功能层面，下一步仍应继续推进上课记录、课后点评、请假和学员详情聚合。但根据 2026-06-25 真实库核查，当前最高优先级需要先处理两个数据正确性风险：学生 `status` 编码错位、班级点名与课表考勤两套 `status` 枚举串味。它们会影响真实数据含义和后续统计，优先级高于继续扩展新页面。

## 2026-06-25 真实库与后端技术债更新

新增文档：`doc/数据库真实结构与后端技术债核查_2026-06-25.md`。该文直连真实 MySQL 库核查了 33 张 `teach_*` / `ast_*` 表，并对照后端代码确认以下结论：

- 真实教学域使用 `teach_*` 表；早期数据库设计文档中的教学 `ast_*` 表基本属于历史设计稿，当前只有物品费用仍使用 8 张 `ast_*` 表。
- 高危问题：班级点名明细表和课表考勤表存在两套 `status` 枚举，`teach_class_service.py` 中存在无映射反写旧考勤表的路径，容易造成“未到/缺勤”等状态口径串味。
- 高危问题：学生 `status` 编码在 DO 和 VO 之间整体错位，存在新建学生状态和在读筛选不一致风险。
- 中高风险：学生、老师、家长、基础用户等旧表软删存在写错 `del_flag` 约定值的问题。
- 已澄清：不存在“双报名台账”双活问题；旧 `teach_courses`、`teach_course_enrollments`、`teach_course_consume_logs` 当前属于死表或历史残留。

因此当前修复优先级调整为：

1. 先修学生 `status` 编码错位，并设计存量数据回填策略。
2. 再修考勤跨表 `status` 映射，避免班级点名写入旧课表考勤时语义串味。
3. 修旧表软删 `del_flag` 约定值和相关查询写法。
4. 然后继续上课记录课后点评、请假、补课和学员详情聚合。

## 已打通的关键链路

### 课程和套餐

- 前端入口：`/assistant/course`
- 后端接口：`/teach/course`、`/teach/course/package`
- 已支持：课程列表、课程详情、新增、编辑、启停、删除、课程选项、套餐列表、套餐详情、新增/编辑/启停/删除。
- 与物品/费用联动：套餐可包含课程、物品和费用。

### 物品/费用

- 前端入口：`/assistant/inventory`
- 后端接口：`/ast/item`、`/ast/inventory`
- 已支持：物品管理、SKU、可售物品选项、库存流水、采购入库、采购导入、领用、退领、盘点、费用管理。
- 关联报名：报名/续费中的物品项会走库存销售出库逻辑。

### 学员报名/续费到班级

- 前端入口：`/assistant/student/enroll/:id`
- 后端接口：`/teach/student/enroll`
- 已支持：选择课程、套餐、物品、费用；课程可选择班级；提交后生成报名订单、订单明细、课程账户。
- 选择班级时：后端校验班级存在、启用、可招生、课程匹配、容量限制，并把学员加入班级。

### 班级基础和未排课点名

- 前端入口：`/assistant/class`、`/assistant/class/detail/:id`、`/assistant/class/attendance/:id`
- 后端接口：`/teach/class`
- 已支持：班级列表、班课/一对一、新增、编辑、删除、充值购时开关、班级学员、可添加学员、添加/移出学员。
- 点名能力：点名准备、提交点名、点名列表、点名详情。
- 当前限制：班级详情中的“排课信息”已经接入真实课次；临时学员、请假、调课、导出等课表高级交互还未闭环。

## 下一步建议

优先级建议如下：

1. 优先继续补上课记录课后点评真实化，或补学员详情中的上课记录/考勤/消费聚合。
2. 再补齐课表高级交互，包括临时学员、请假、调课、冲突确认、导出签到名单和课表。
3. 然后处理老师详情 404、老师课时统计、缺课补课操作和批量分配/导入等低频但容易误导的入口。

不建议现在先开会员卡或场地管理。那两个模块是新域，短期会扩大战线；而课表和上课记录是当前班级闭环自然缺口，完成后整个教学主链路会明显更稳。
